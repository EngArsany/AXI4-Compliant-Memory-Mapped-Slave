# AXI4-Compliant Memory-Mapped Slave — Design & Verification Notes

## 1. System Overview

Two-module DUT:

- **`axi4_slave`** — protocol engine. Decodes AW/W/B (write) and AR/R (read) channels, runs burst FSMs, enforces 4KB-boundary and range checks, drives memory control signals.
- **`axi4_memory`** — synchronous single-port RAM. 1024 × 32-bit words = 4KB total. Word-addressable only (byte address >> 2).

No arbitration, no interconnect, no outstanding-transaction support — single AXI master (your TB) talks directly to one slave. This is a **subset** of full AXI4 (see §5, unsupported features).

## 2. Interface Signals (fixed widths in this design)

| Group | Signals | Width | Direction (slave) |
|---|---|---|---|
| Global | ACLK, ARESETn | 1 | in, in (active-LOW async/sync reset — confirm in RTL) |
| AW | AWADDR, AWLEN[7:0], AWSIZE[2:0], AWVALID/AWREADY | ADDR=16b* | in/in/in/in-out |
| W | WDATA[31:0], WLAST, WVALID/WREADY | 32b | in |
| B | BRESP[1:0], BVALID/BREADY | 2b | out |
| AR | ARADDR, ARLEN[7:0], ARSIZE[2:0], ARVALID/ARREADY | ADDR** | in |
| R | RDATA[31:0], RRESP[1:0], RLAST, RVALID/RREADY | 32b/2b | out |

\* Spec table header says AWADDR[15:0]/16 in one place but body text says ARADDR[31:0]/16 — **inconsistency in the source spec**. With a 4KB (12-bit) memory window, only `ADDR[11:0]` is meaningfully decoded regardless of bus width; clarify actual RTL port width before writing the interface/agent — don't assume, check the `.sv` port list.
\** Same width ambiguity as AWADDR — verify against RTL.

- No WSTRB in the signal table — **byte strobes are apparently NOT implemented**, even though the general AXI4 description (page 1) advertises byte-strobe support as a protocol feature. This design likely only supports full-word (AWSIZE=3'b010, 4-byte) writes. Confirm in RTL; if WSTRB is absent, partial-word writes are impossible and any AWSIZE/WSTRB coverage bins for sub-word access are **not applicable / excluded**.
- No AWID/ARID/BID/RID, no AWBURST/ARBURST (burst type: FIXED/INCR/WRAP) in the given table — burst type may be hardwired to INCR only. Verify; if BURST type isn't a port, WRAP/FIXED burst-type coverage is out of scope.
- AWREADY/ARREADY are described as tied HIGH by default "to improve timing efficiency" — i.e., the slave is always ready to accept address+control (single-cycle AW/AR phase, no backpressure on those two channels). This matters for handshake-order coverage (VALID-before-READY is structurally forced here since READY is already high).

## 3. Protocol Handshake Rule (applies to all 5 channels)

Transfer occurs only when **VALID && READY** are both HIGH on the same clock edge.
- Source must not wait for READY before asserting VALID... but is also not required to assert VALID until data is ready — however once VALID is asserted it **must stay HIGH until the transfer completes** (no de-asserting VALID before the matching READY arrives — classic AXI illegal-sequence check).
- Three legal handshake timing relationships: VALID-before-READY, READY-before-VALID, VALID-with-READY simultaneously.
- **Verification-critical rule**: VALID must never be *retracted* or have its payload changed while asserted and unacknowledged. This is a standard AXI protocol assertion to implement (`AXI4_VALID_STABLE`).

## 4. Write Channel FSM Behavior

1. **W_IDLE / Address phase**: on `AWVALID && AWREADY` (AWREADY is default-1), slave latches AWADDR, AWLEN, AWSIZE. Moves to data phase.
2. **Data phase**: WREADY asserted after WVALID is observed high (not necessarily combinational default-1 like AW — check exact timing in RTL, it says "sets WREADY after recognizing WVALID is high", implying **1-cycle latency**, i.e. WREADY is NOT default-high on W channel, unlike AW/AR). This is an important asymmetry to verify: AW/AR are zero-latency ready, W is not.
   - Per beat: if `(addr>>2) < 1024` AND burst does not cross 4KB boundary → `mem_we=1`, data written.
   - If out of range / boundary violation → no write, error response latched for later.
   - WLAST must be asserted by master on final beat; total beats = `AWLEN + 1`.
3. **Response phase**: after WLAST beat consumed → WREADY deasserted, BVALID=1, BRESP = OKAY or SLVERR (EXOKAY/DECERR are defined in the RESP encoding but **not generated by this design** — only 2 of 4 responses are reachable → mark EXOKAY/DECERR bins as excluded/unreachable in coverage).
4. On `BVALID && BREADY` → FSM returns to W_IDLE.

**Pitfall to check in RTL/TB**: what happens if boundary violation occurs mid-burst on beat N (not beat 0)? Does the whole burst get SLVERR, or does it write beats 0..N-1 and only fail from N onward? Spec text is ambiguous — this is a question to resolve with the DUT author or by RTL inspection before writing the scoreboard/checker, since it changes expected-memory-content modeling significantly.

## 5. Read Channel FSM Behavior

1. **R_ADDR**: on `ARVALID && ARREADY` (ARREADY default-1), latch ARADDR/ARLEN/ARSIZE, validate range+boundary immediately.
2. **R_DATA**: each cycle, if access valid: read `mem_rdata`, drive RVALID=1, RDATA=value, RRESP=OKAY, same cycle (combinational/registered read — confirm memory read latency: "synchronous" RAM implies 1-cycle read latency, meaning RDATA in R_DATA is technically the data addressed by the *previous* cycle's `mem_addr` — verify address/data phase pipelining doesn't cause an off-by-one on the first beat).
3. RLAST=1 on the final of `ARLEN+1` beats.
4. Beat advances only on `RVALID && RREADY`.
5. **TB-side rule explicitly called out in spec**: after sampling RVALID de-assertion, the TB must de-assert RREADY the very next cycle (not same cycle) — an explicit sequencing requirement for the driver/monitor.
6. **Error path**: out-of-range or boundary-crossing read → RDATA=0, RRESP=SLVERR, RLAST=1, single-beat error response (whole burst reduced to one error beat, not continued for remaining beats — confirm this against RTL, since it differs from the write path where the ambiguity is about mid-burst failure).

## 6. Address / Boundary Rules (core thing to verify)

- **4KB boundary check**: `AWADDR`/`ARADDR` + burst extent must not cross a 4KB (0x1000) boundary — mandated by AXI4 itself, independent of this design's total memory being exactly 4KB. Because the whole memory *is* 4KB, in practice this reduces to "does the burst run past the end of the single memory region," but conceptually it's still the generic AXI 4KB-boundary rule and should be tested as such (e.g., a start address near 0xFF8 with a long burst).
- **Range check**: `(addr >> 2) < 1024` (MEMORY_DEPTH parameter). Byte address is converted to word address by `>>2` — i.e. hardware assumes **word-aligned, full-word (4-byte) accesses only**.
- **AWSIZE/ARSIZE is effectively fixed** at `3'b010` (4 bytes) since the datapath is 32-bit only. The spec explicitly flags this as an open question ("it needs to be fixed at what?") — meaning: verify what the RTL actually does if AWSIZE/ARSIZE ≠ 2 is driven. Likely candidates: (a) RTL ignores AWSIZE/ARSIZE entirely and always transfers 4 bytes (spec/DUT mismatch — a real bug to find), or (b) RTL has an implicit assumption/assertion that AWSIZE==2. **This is a prime target for a directed test + assertion**: drive AWSIZE/ARSIZE = 0,1,3..7 and observe actual behavior.
- Unaligned addresses (`addr[1:0] != 0`) — behavior undefined by spec text ("may lead to invalid memory operations or ignored transactions"). Needs a directed test to characterize actual DUT behavior and either assert it's rejected (SLVERR) or document it as a known limitation.

## 7. Memory Model (`axi4_memory`)

- Word-addressable, depth 1024, 32-bit width, single port, synchronous.
- `mem_en`, `mem_we` control read/write; `mem_we=1` → write, else read (per spec text "vice versa" — confirm read requires `mem_en=1 && mem_we=0`, not just `mem_en`).
- Single port ⇒ **no simultaneous read+write**; slave FSM must serialize AW/W and AR/R access to memory — good candidate for a structural assertion (mem_we and a concurrent read request never overlap) if the FSM doesn't already make this impossible by construction.

## 8. Response Encoding Actually Reachable

| RESP | Meaning | Generated by this design? |
|---|---|---|
| 2'b00 OKAY | success | Yes |
| 2'b01 EXOKAY | exclusive access success | No (no exclusive access support) |
| 2'b10 SLVERR | slave error (range/boundary) | Yes |
| 2'b11 DECERR | decode error | No (no address decoder / no multiple slaves) |

Functional coverage on BRESP/RRESP should have 4 bins but **only 2 are legally hittable** — exclude EXOKAY/DECERR with written justification per the deliverable requirements (page 11: "Provide a clear and justified report of uncovered bins").

## 9. Key Verification / Testbench Requirements (from spec, project goals)

Architecture mandated:
- Class-based transaction (`axi4_packet`) encapsulating AWADDR/AWLEN/AWSIZE/WDATA/WSTRB(if present)/ARADDR/ARLEN/ARSIZE, response fields, etc.
- Constrained-random stimulus generator, driver, monitor, checker/scoreboard, functional coverage collector — standard CDV layered environment.
- SV `interface` with `modport`s for master/slave/monitor signal direction.
- Concurrent SVA assertions for handshake/protocol rules (VALID stability, READY behavior, RLAST/WLAST correctness, no X/Z on VALID-qualified signals, etc.).

Coverage goals (deliverable-mandated):
- 100% functional coverage (burst lengths, AxSIZE values driven, address regions incl. near-boundary, both write & read directions, both response types) unless justified exclusion.
- 100% code coverage: line, toggle, branch, condition/expression.
- 100% assertion coverage.
- Documented, justified list of any unreachable/excluded bins (EXOKAY, DECERR, non-word AxSIZE if RTL hard-ignores it, etc.).

## 10. Test-Case Checklist to Derive From This Spec

- Legal single-beat and max-length burst (AWLEN=255) write/read, in-bounds.
- Burst that starts legally but would cross the 4KB boundary → expect SLVERR (write) — **clarify partial-write-then-error vs. full-suppress behavior with RTL owner before writing checker**.
- Read burst crossing boundary → single SLVERR beat with RLAST=1, RDATA=0.
- Address at exact last valid word (offset 0xFFC) single-beat access — boundary edge case.
- Out-of-range address (>4KB) both directions.
- AWSIZE/ARSIZE ≠ 3'b010 driven — characterize actual RTL response (bug-hunting case).
- Back-to-back transactions (write immediately followed by read of same address) — data-integrity/ordering check, single memory port.
- BREADY/RREADY held low after VALID asserted — verify master-side backpressure doesn't corrupt DUT state (VALID must remain stable while waiting).
- VALID de-asserted early (illegal on master side) — assertion should fire in TB driver's own protocol-checker, or in monitor if used to catch a misbehaving test.
- Reset (ARESETn) assertion mid-transaction — verify FSM returns to idle safely, no dangling VALID left asserted.
- WREADY latency check: confirm 1-cycle delay after WVALID vs. AWREADY/ARREADY 0-cycle default, since this asymmetry is explicitly stated in the spec and easy to get wrong in the driver's expected-timing model.

## 11. Open Items to Confirm Against RTL (don't assume from spec text alone)

1. Actual bit-width of AWADDR/ARADDR ports (16 vs 32 — spec self-contradicts).
2. Presence/absence of WSTRB.
3. Presence/absence of AWID/ARID/BID/RID and AxBURST.
4. Exact behavior on mid-burst boundary violation (write path).
5. Exact behavior when AWSIZE/ARSIZE ≠ 2.
6. mem_en/mem_we exact truth table (is `mem_en` required for reads, or does `mem_we=0` alone imply read regardless of `mem_en`?).
7. ARESETn: synchronous or asynchronous reset in the FSM/memory.
